# quad_trie_descent

深さ 8 の四分木 (各ノードの子リスト、`[-4]` 定数アクセス + ゴミノード append で掘る方式) について、
ランダムな ID (0..65535) から末端ノードまで掘る 2 方式を同一条件で比較する。

`random_access:list_mapped_trie` が同じ掘り方の二分木版 (1 bit / 層・16 層) なので、
そちらと並べて読むと「1 層あたりの bit 数」を変えたときの効き方が分かる。

## 木の形

`storage _ c` は 9 レベルのリストの入れ子。レベル 0 が `c` 自身、レベル 8 が末端 (空リスト)。
各ノードは子を 4 個持つ。4^8 = 65536 なので ID 0..65535 と末端が 1:1 に対応する。

末端まで list 型で統一しているのは NBT の制約による。NBT のリストは同一型の要素しか
持てないため、末端を数値にすると最下層ノード (数値のリスト) への空ノード append が
型不一致で落ちる。全階層を list にしておけばどの層への append も通る。

## 掘り方 (共通部分)

ノードは常に子 4 個。空ノードを r 個 append すると長さが 4+r になり、`[-4]` の指す位置が
index r にずれる。これで「r 番目の子を選ぶ」を定数パスだけで実現している。
次の run のために、そのノードを訪れた直後に `[4]` の remove を 3 回打って長さを 4 に戻す。
ゴミは「自分のノードを次に訪れたとき」に消えればよいので、これで各ノードの長さは
常に 4〜7 に収まる。

層あたりの data コマンドは remove x3 + 条件付き append x3 = 6 本。
remove は無条件に 3 回打つため、ゴミが 0〜2 個しか無いノードでは残りが失敗する。
失敗コマンドのコストも計測に含まれる点に注意 (二分木版も同じ性質なので方式間の比較には影響しない)。
二分木版は層あたり 2 本 x 16 層 = 32 本、四分木版は 6 本 x 8 層 = 48 本。
逆にスコア演算 (シフト) は 16 本 → 8 本に減る。ここが本ベンチの見どころ。

## 計測対象

| 関数 | 内容 |
|:--|:--|
| `upper_mul` | 方式 A。ID を 65536 倍して上位ビット側に寄せ、符号付き範囲判定で 2 bit ずつ切り出す |
| `upper_mul_tmp` | 方式 A の変種。ID を `p` に残したまま一時変数 `t` を潰して掘る (差は先頭の 1 コマンド) |
| `lower_mod` | 方式 B。層ごとに `4^(7-k)` で div してから `% 4`。一時変数 1 本 + 定数 8 本 |
| `lower_mod_tmp8` | 方式 B の別定式化。下位桁から 8 桁ぶんを一時変数に展開してから上位順に消費。一時変数 8 本 + 定数 1 本 |

いずれも `random value 0..65535` で ID を引く部分を関数内に含めている
(`random_access:list_mapped_trie` と同じ構成にして比較可能性を保つため)。

## 子の並び順の違い (重要)

方式 A が選ぶ子インデックスは「符号付き整数としての昇順の順位 rank」であって、
2 bit の桁 d そのものではない。`rank = (d + 2) % 4`、つまり子 0,1,2,3 はそれぞれ
桁 2,3,0,1 に対応する。方式 B は桁 d をそのまま子インデックスにする。

どちらも ID → 末端の全単射なので trie としてはどちらも正しい (木を書く側が同じ規約で
書けばよい) が、**同じ ID でも A と B が到達する末端は異なる**。掘るコストの比較には
影響しない。

桁順を揃えたいなら各層で bit31 を反転させれば符号付き順序と符号なし順序が一致するが、
層あたり 1 コマンド増えるのでここでは採用していない。

## 検証

`/function quad_trie_descent:verify` (`@benchmark` なし)。

1. 方式 A の層ごとの rank が div/mod で求めた期待値と一致するか
2. 実際にストレージを掘って、ちょうど深さ 8 に到達するか (深さ 9 は解決できないこと)

結果は `say` でサーバログに出る。詳細は関数の外から `/data get storage _ v` を直接実行して確認する
(関数内の `data get` はコマンド出力が抑制されるため見えない)。

## 結果の読み方

- `upper_mul` vs `lower_mod` … 「上位から寄せて符号で判定」と「div/mod で桁を取り出す」の差。
  data コマンドの本数 (48 本) は両者同じで、差はスコア演算の本数 (8 本 vs 24 本) だけ。
  差が data コマンドの支配で埋もれるようなら、掘りのコストは NBT パス解決が律速だと言える。
- `lower_mod` vs `lower_mod_tmp8` … 定数 8 本 + 一時変数 1 本 と、定数 1 本 + 一時変数 8 本の差。
  スコア演算の本数はほぼ同じ (24 本 vs 22 本) なので、有意差が出たらスコアホルダー側の
  ハッシュ / キャッシュの効果ということになる。
- `upper_mul` vs `upper_mul_tmp` … `scoreboard players operation = ` 1 本ぶんの値段。
  ID を保持したまま掘る実装にしたときの追加コストの目安。
- `random_access:list_mapped_trie` (二分木・16 層) と並べる … 層あたりの bit 数を 1 → 2 に
  したとき、data コマンド 32 → 48 本 / スコア演算 16 → 8 本のトレードオフがどちらに転ぶか。
