# nested_path_access

`[-4]` のネスト深さ 1〜8 でのストレージアクセスコストを測る。
「1 段潜るのにいくらかかるか」を読み出し側と書き込み側の両方で取る。

`quad_trie_descent` の掘りは 8 段ぶんの `[-4]` を積むので、そこで出た数字の
内訳をここで分解できる、という位置づけ。

## 構造

- `n` … レベル 0 (= `n` 自身) からレベル 8 までの 9 段。各ノードは要素 4 個。
  読み出しベンチ `depth_1` .. `depth_8` はこの木を使う。
- `w1` .. `w8` … `w<d>` はレベル 0 から d までの d+1 段。
  つまり `w<d>[-4]` を d 回たどると必ず末端に着く。
  書き込みベンチ `depth_1w` .. `depth_8w` はこちらを使う。

末端まで list 型で統一しているのは NBT のリストが同一型の要素しか持てないため。

### なぜ書き込みだけ木を分けているか

`n` の内部ノードを `data modify ... set value` で上書きすると、その下の部分木が
丸ごと消えて木が壊れる (ベンチは同じ関数を何万回も回すので 1 回でも壊れると以降が無意味になる)。
深さごとに「そこがちょうど末端になる木」を用意すれば、末端の値だけを書き換えられるので
構造を壊さずに済み、読み出し側と同じ「`[-4]` を d 回たどる」パス解決コストだけを取り出せる。

## 計測対象

| 関数 | 内容 |
|:--|:--|
| `depth_1` .. `depth_8` | `data get storage _ n[-4]...` (深さ d)。1 関数につき 4 回 |
| `depth_1w` .. `depth_8w` | `data modify storage _ w<d>[-4]... set value ...` (深さ d)。1 関数につき 4 コマンド |

1 関数あたり 4 コマンドにしているのは、関数呼び出しのオーバヘッドを薄めるため。
書き込み側は `[0]` と `[]` を交互に書いて元に戻す (`list_index_access` と同じ形)。
同じ値を続けて書かないので「変化なし」判定には当たらない。

読み出し側は d < 8 では部分木 (要素数 4 のリスト)、d = 8 では末端 (空リスト) を指す。
`data get` がリストに対して返すのは要素数なのでどちらも O(1) だが、返る値の意味は違う。

## 検証

`/function nested_path_access:verify` (`@benchmark` なし)。

1. `n` の各層がちょうど 4 要素か (`[3]` が在る / `[4]` が無い)
2. `n` の深さがちょうど 8 か (深さ 8 は解決でき、深さ 9 は解決できない)
3. `w<d>` の深さがちょうど d か
4. `depth_<d>w` を通しても `w<d>` の構造が壊れず、末端が `[]` に戻っているか

## 結果の読み方

- **depth_d を d について並べたときの傾き** が「`[-4]` 1 段ぶんの値段」。
  切片がコマンド 1 本の固定費 (パース済みコマンドのディスパッチ + ストレージ取得)。
  傾きが切片に比べて十分小さければ、深いネストそのものは大して高くない、と言える。
- **線形からのズレ** … 深いほど 1 段が高くなるなら、パス解決がノードを辿るたびに
  キャッシュミスしていることになる (木が大きくなるほど効く)。
  逆に線形なら、コストはコマンド 1 本の固定費が支配的。
- **depth_d vs depth_dw** … 同じ深さでの読み / 書きの差。
  書き込み側にはコピーオンライトやダーティフラグのコストが乗る可能性がある。
  差が深さによらず一定なら「書き込みの固定費」、深さに比例して開くなら
  「パスを 2 回たどっている」等の疑いが持てる。
- **quad_trie_descent との突き合わせ** … 掘り 1 回は深さ 1..8 のパスを 1 本ずつ
  積んだ形になるので、depth_1..depth_8 の合計と比べると掘りの中で
  パス解決が占める割合が見積もれる。
